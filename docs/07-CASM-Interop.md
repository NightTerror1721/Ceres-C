# C and CASM in one program

[← Back to index](README.md)

A Ceres-C program does not have to be all C. A routine written by hand in CeresASM can be called
from C, a C function can be called from assembly, and both kinds of file are named on the same
command line:

```sh
ceresc io.c hello.c triple.casm banner.casm -o hello.cres --run
```

[`examples/interop/`](../examples/interop) is exactly that program, and it is the shortest way to
see the whole arrangement working.

## The rule that makes it work: names are names

**A C symbol keeps its own name in the generated assembly.** `int triple(int)` is `triple`. No
prefix, no decoration, nothing to look up.

So the two sides meet in the middle. Assembly publishes a symbol with `global`:

```casm
@text

global triple:
    add r1, r0, r0      // r1 = 2n
    add r0, r1, r0      // r0 = 3n
    ret
```

and C declares it with `extern`, which says "defined elsewhere, reserve nothing here":

```c
extern int triple(int n);
```

The argument arrives in `r0` and the result goes back in `r0` because that is
[CeresASM's own calling convention](https://github.com/Krampus1721/CeresASM/blob/main/docs/24-Calling-Convention.md),
which Ceres-C follows rather than inventing one. Up to four integer arguments travel in `r0`–`r3`
(floats in `f0`–`f3`, counted separately), the rest on the stack, and the result comes back in `r0`
or `f0`.

### The one thing you cannot name

A handful of words are reserved by the assembler's own lexer and cannot be read as an identifier:
`let`, `const`, `global`, `import`, `macro`, `endmacro`, `alias`, `struct`, `endstruct`, `align`,
`org`, `assert`, `interrupt`, the type names (`u8`, `u32`, `f32`, `ptr`, `char`, `bool`, `string`,
`port`, `irq`, `byte`, `half`, `word`), `true`, `false`, and the register names (`r0`–`r15`,
`f0`–`f15`, `sp`, `fp`, `at`, `lr`).

A C function or global named one of them is a Ceres-C error, with a message saying so. It is a
narrow price for names that mean the same thing on both sides — and most of that list is already a C
keyword anyway.

Instruction mnemonics are **not** reserved: a function called `add` or `print` is fine, because a
mnemonic is only a mnemonic in instruction position.

## Calling C from assembly

An object cannot name a symbol it has never seen declared. The assembler picks an opcode from the
*shape* of an operand — `mov r1, counter` encodes differently depending on what `counter` is — long
before anything has an address, so a bare `call put` in a unit that never saw `put` is an
"Unresolved symbol" at assembly time, not a job for the linker.

Ceres-C writes that declaration for you. Every build of more than one file produces a declarations
file next to the output, named after it:

```
ceresc io.c hello.c ... -o hello.cres      →      hello.decls.casm
```

```casm
// Generated by ceresc. Declarations only - no code and no storage.

@bss
global let writeCount: u32

@text
global put:
global putstr:
global putint:
global main:
```

Every generated `.casm` imports it automatically. A hand-written one does the same to reach the C
side:

```casm
import "hello.decls.casm"

@text
global showBanner:
    ...
    call put
    ret
```

An `import` in a unit being assembled on its own contributes **no bytes** — only names and shapes.
That is why importing declarations of symbols the same unit defines is not a redefinition, and why
the declarations file is never itself assembled into an object.

## Sharing variables

An `extern` declaration in C and a `global let` in assembly are the same statement about the same
object, from the two sides:

```c
extern int writeCount;        // io.c defines it; every other unit declares it
```

```casm
ldv r1, writeCount            // assembly reads the very same object
```

`const` globals live in `@rodata`, where a store raises `MemoryFault` — so assembly that writes
through a pointer to one faults, exactly as the qualifier says it should.

## Code that was built before

A hand-written `.casm` names the C side through the declarations file. The other direction — C calling into an
object or archive built earlier — needs the same kind of file, and `ceresc` can neither compile nor read a
`.cobj`: `--emit-decls` writes one for the C it compiles, and `--decls` hands it to a later build together with the
`.cobj` or `.car` itself. See [05-CLI.md](05-CLI.md#linking-code-built-earlier).

## What the build actually does

```
ceresc io.c hello.c triple.casm banner.casm -o hello.cres --run
```

1. Preprocesses and compiles each `.c`, writing `io.casm` and `hello.casm` next to their sources.
2. Writes `hello.decls.casm` and puts an `import` of it at the top of each generated `.casm`.
3. Runs `ceres asm -c` on every `.casm` — generated and hand-written alike — producing one `.cobj`
   each.
4. Runs `ceres link` over all of them into `hello.cres`.
5. Runs `ceres run hello.cres`.

Every step is a real subprocess. Ceres-C never links against CeresASM's libraries; it invokes the
`ceres` binary exactly as you would, which is why the commands above are the ones you can run
yourself when something goes wrong.

Without `--run` it stops after step 2, and the `.casm` files are yours to assemble however you like.

## Caller-saved registers

`call` destroys `r0`–`r7`, `r12`, `f0`–`f7`, `at` and the flags. Assembly calling into C has to save
anything it wants to keep across that call — the same rule C code follows, only here you are the one
applying it:

```casm
    push r5             // `put` is a C function: it may clobber r0-r7
    call put
    pop  r5
```

Getting this wrong produces a wrong answer rather than a crash, which is why
[`examples/interop/banner.casm`](../examples/interop/banner.casm) says so in a comment at the point
it matters.
